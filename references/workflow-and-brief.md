# 工作流程与 brief

## 工作目录（固定约定）

所有产物都放在项目根目录下。H3 之前的候选图、预览和报告只进 `work/render/`；只有 H3 已批准且版本匹配的实际成图与说明才进入 `outputs/`。

```text
<项目根>/
├─ outputs/                        最终交付物（只有这里的东西给用户）
│  ├─ KV-CN-4x5.png                H3 批准的中文版主视觉
│  ├─ KV-EN-4x5.png                H3 批准的英文版主视觉
│  ├─ KV-CN-16x9.png               仅 H1 批准横版时使用
│  ├─ KV-EN-16x9.png               不覆盖其他比例的已有成图
│  └─ 交付说明.md                   受众/主张/证据/价格与时间来源/批准版本
└─ work/
   ├─ input/                       用户原始素材：包装图、实拍图、logo、资质、活动规则截图
   ├─ brief/kv-brief.md            结构化 brief（唯一的需求真相源）
   ├─ spec/kv-cn.json              中文版设计规格（排版的唯一真相源）
   ├─ spec/kv-en.json              英文版设计规格（与 CN 同坐标，仅换文案）
   ├─ base/                        底图：base-cn.png（实拍/抠图合成/生图）与 optional 细节图
   └─ render/                      迭代稿、对比图、report.json
```

规则：

- 规格 JSON 是唯一真相源。改图 = 改 spec 重渲染，不要直接修 PNG。
- 中英双版共用 H1 批准的比例、像素尺寸、底图和核心骨架；英文可改文字框宽度、字号、换行，不得改变画布或商品比例。
- 底图一律放 `work/base/`，不进 `outputs/`。

## 七步流程（跨轮次执行）

七步流程跨多个回复执行。每轮最多执行至下一个尚未获真实用户批准的 Human Gate；提交 Gate 材料后必须结束当前回复并等待用户新消息。模型在 Brief、报告或交付说明中自行写入的 `Approved` 不构成批准证据；一般性的“请完成整个任务”也不等于预先批准。

1. **建档与事实分析**：建目录，把用户给的素材放 `work/input/`；检查商品参考图、品牌资产、事实和文案。素材是图片时先看清楚再引用，不要凭文件名猜内容。
2. **写 brief 并提交 H1 输入基线确认后停轮**：附 Reference/Facts Inventory、产品保真模式、Project Style Constraint Record 与 Canvas Specification 初稿。默认 4:5；用户明确指定 16:9 时不得改回竖版；与目标平台硬限制冲突则在 H1 求确认。只有涉及促销时核验价格与时间。无用户针对该版本的批准不得进入步骤 3。
3. **定受众与单一主张**：一句话写完「给谁 / 什么场景 / 解决什么 / 为什么现在买」。主标题只承载一个核心价值，支撑卖点最多 3 条；在 H1 约束内形成沟通层级。
4. **提出创意方向并提交 H2 选择/冻结后停轮**：仅在 H1 获批后执行。默认并列提交 A、B、C 三套针对批准比例独立构图的方案与简短比较；横竖版分别考虑重心、文字区、支撑面、留白、信息层级与动线，不能把竖版骨架拉伸/裁切成横版。提交后保持 H2 `Pending`，除用户明确请求的概念预览外不得正式制作。
5. **定底图并制作**：仅在 H2 获批后执行。批准的实拍/商品参考优先；有实拍无场景就抠图 + 画布合成；AI 生图只能提供无商品、无文字的场景底图。没有可靠商品依据时只做规划或明确标注的非保真布局稿（见 `references/photo-base.md`）。中英双版共用同一张底图。
6. **写规格并渲染**：竖版改造现有模板，横版由 `landscape-concept-*.json` 或获批的横版方案独立排布并替换所有占位内容；CN/EN 保持同尺寸、底图和骨架、相同 `--scale`。候选渲染只放 `work/render/`，必须打开成图看。
7. **技术 QA、提交 H3 实际成图审核后停轮**：跑 `scripts/verify_kv.py`，逐条过 `references/quality-gate.md`，再由人工审核实际 CN/EN 成图。支撑接触、接触阴影或媒介关系不成立时先返工，不能提交 H3。提交 H3 后结束当前回复；只有下一轮收到用户针对对应实际图像版本的明确批准，才可写交付说明并放入 `outputs/`。

## Human Gate 记录契约

三个 Gate 都必须写入现有 Brief、Visual Strategy、Rendered QA 或交付说明，至少记录：`Submitted version`、`User message evidence`、`Approved scope`、`Decision`、`Result version`、日期/决策人（如适用）。没有真实用户批准消息时记录为 `Pending`，不得继续；AI 技术 QA、脚本 `PASS`、`READY` 或模型自行填写的 `Approved` 都不是人工批准。

### H1 输入基线确认

- AI 提交：素材/事实/文案清单，商品参考图和品牌资产状态、促销是否相关、保真模式、缺口/冲突，以及 Project Style Constraint Record 与 Canvas Specification 初稿；提交后结束回复。
- 人确认：可用证据、官方字体/品牌色/禁用元素、必要商品事实和任务类型，以及画布用途/目标平台、比例、像素尺寸、方向、PNG、平台附加限制和规格来源。
- 决策：`Approved` / `Changes requested` / `Returned`；必须有用户针对该提交版本和范围的明确消息，否则为 `Pending`，停在步骤 2。
- 回退：`Changes requested` 回步骤 1–2；`Returned` 回步骤 1，必要时转规划模式。

### H2 创意方向与项目风格冻结

- AI 提交：默认一次性提交 A/B/C 三套创意方案和横向比较，更新 Style Constraint Record 中的候选项；可以推荐一套并说明理由，但不得自行选择、冻结或标记为 `Approved`。用户明确只需要一套或两套时按其要求；实际约束不足以支持三套合理方案时说明原因，不为凑数编造差异。提交后必须在同一条回复末尾展示完整的四类操作入口，并结束当前回复。
- 人确认：可直接批准 A/B/C 中某一明确版本；选择一套并要求局部修改；组合不同方案的策略；要求重新提案；或指定全部/部分方案请求低保真预览。全局硬约束与 H1 的品牌硬约束始终优先。
- 决策：`Approved` / `Changes requested` / `Returned`；只有用户在看到提交材料后明确批准具体方案 ID、版本和范围，才能冻结方向。“请继续”“请完成任务”“先生成看看”、模型自行记录的批准及“授权制作概念预览”均不构成 H2 `Approved`。
- 回退：修改、组合或重新提案属于 `Changes requested`，回步骤 3–4 形成新的方案 ID/版本并再次提交；`Returned` 回步骤 1–2。H2 `Pending` 时，除明确请求的概念预览外，禁止生成正式背景、正式成图或进入步骤 5。

#### H2 回复末尾标准交互格式（必须）

每次提交 H2 方案后，回复结尾必须同时列出以下四类操作，不能只展示 AI 推荐方案的批准入口：

1. **直接批准**：批准某个明确方案 ID/版本。
2. **修改/组合/重新提案**：说明要修改的方案 ID/版本、要组合的部分，或要求重新提出方案。
3. **模式 A 预览**：使用本地脚本、模板和简单图形制作低保真构图草图，不调用在线生图。
4. **模式 B 预览**：用户明确授权后，调用可用图片生成工具制作低保真场景氛围预览。

模式 A 和模式 B 都必须说明：用户可以只指定部分方案，也可以预览全部方案；预览仍属于 H2 决策阶段；预览授权不等于正式批准；H2 继续保持 `Pending`，正式制作不得提前开始。默认仍不生成图片，只有用户明确提出对应请求（模式 B 还需明确授权）才执行。方案预览完成后仍须用户针对明确方案 ID/版本发出 `Approved` 才能冻结方向。

结尾必须提供可以直接复制的示例，例如：

```text
批准 A-v1
修改 B-v1 的标题字体
结合 A-v1 的构图与 C-v1 的信息层级
使用模式 A 预览 A-v1、B-v1、C-v1
授权使用模式 B 预览 B-v1
```

#### H2 方案结构与横向比较

每套方案用相同的简洁结构，便于用户比较：

1. 方案 ID、版本与名称。
2. 风格关键词、核心主张与目标受众。
3. 视觉骨架、商品位置和占比。
4. 场景媒介、真实支撑面、接触关系与光线方向。
5. 中文/英文字体候选、主色与强调色。
6. 标题、卖点、价格、CTA 的信息层级；只列任务实际需要的字段，不为套模板添加促销信息。
7. 方案优势、潜在风险与制作可行性。

三套方案须在摄影/编辑策略、视觉骨架、构图、场景、字体、配色或信息层级中的多个关键维度形成实质差异，不得只换颜色、名称或装饰。每套都必须遵守 H1 已确认的产品事实、品牌硬约束、素材授权、商品保真与目标平台限制；A–H 骨架只是候选资源，不要求固定使用三个骨架，也不要求不同商品套用同一组三风格。并列方案之后附一张简短比较表，指出主要差异、适用目标、风险与成本，再停止回复并保持 H2 `Pending`。

#### 选择、修改与冻结

- 用户直接批准某个方案时，批准消息必须指向方案 ID 与版本；记录 `User message evidence`、批准范围和结果版本后，才冻结该方向。
- “选 B，但修改字体”是修改请求，不是对原 B 的批准；产出 B 的新版本并再次等待确认。
- 组合 A 的构图与 C 的字体时，建立新的组合方案 ID/版本，写清继承项与变化项，再次提交 H2。
- 正式制作只使用已冻结方案，不得擅自混入未选候选。批准范围内的局部字号、间距和位置微调不必重开 H2；改变核心风格、骨架、字体策略或配色方向时，必须提交新版本重新批准。

#### H2 可选低保真概念预览

预览是 H2 内的辅助决策，不新增 Gate。默认不生成；只有用户明确要求并指定要预览的方案后，才能执行。用户可以只预览 A/B/C 的一部分。

**模式 A：轻量构图与风格草图**

- 优先使用已有 Python 脚本、模板或简单图形，不调用在线图片生成模型。
- 可展示商品占位、色块、文字区域、视觉重心、字体候选、配色和场景位置。有已获批准的商品参考图时可使用原图；否则只能使用明确标识的商品占位框。
- 只比较布局和风格结构，不宣称完整摄影真实感。

**模式 B：AI 氛围概念预览**

- 只有用户明确授权模式 B 后才调用可用的图片生成工具；只生成无商品、无文字的场景背景，不重构真实商品、Logo 或产品结构。
- 可把获准的真实商品素材叠加到背景上形成概念预览；不得默认执行完整中英双版正式生产。

两种模式都使用 H1 批准的画布比例和商品事实；模式 A 横版可在同一 16:9 画布上用简单图形排出文字区、商品占位、支撑面和方案 ID 以比较布局，不能用竖版占位图拉伸。模式 B 应按获批比例规划场景；工具仅返回其他尺寸时合理重构空场景，不能拉伸真实商品。以能比较为限控制分辨率、次数与成本；后期加方案 ID、版本和 `CONCEPT / NOT FINAL`。预览只存 `work/render/`，不进 `outputs/` 或 H3；展示后结束回复并保持 H2 `Pending`。预览授权不等于批准。

模式 B 若遇权限错误、接口不兼容或其他服务失败，停止重复调用该失败路径，如实报告原因和已完成工作，保留三套提案与 H2 `Pending`。可以建议改用模式 A；未经用户同意，不得切换图库照片、其他生图服务或虚构预览结果。外部服务不可用不代表 H2 已通过，也不代表方案本身失败。

### H3 实际成图审核

- AI 提交：实际 CN/EN 全尺寸图与缩略图、对应 spec/底图版本、技术 QA 报告、视觉问题清单、产品参考对照、支撑接触/阴影检查、媒介一致性检查及促销事实来源（如适用）；提交后结束当前回复。
- 人确认：产品保真、构图、产品显著性、文字层级、可读性、真实场景关系、品牌约束、双版事实一致性，以及是否进入 `outputs/`。
- 决策：`Approved` / `Changes requested` / `Returned`；必须有用户针对实际图像版本和范围的明确消息，否则为 `Pending`，候选图继续留在 `work/render/`。
- 回退：`Changes requested` 回步骤 5（底图/合成）或步骤 6（spec/渲染）；支撑面分离、接触阴影不成立或未经批准的摄影/插画媒介冲突必须回步骤 5–6。`Returned` 回步骤 3–4，若事实或证据失效则回步骤 1–2。

## Canvas Specification（Brief 项目级记录，H1 确认）

| 字段 | H1 初稿默认值 / 确认方式 |
| --- | --- |
| 用途 / 目标平台 | 写实际用途、平台；未知则记录未提供 |
| ratio / width / height | 默认 `4:5` / `1200` / `1500`；用户明确要求横版时建议 `16:9` / `1920` / `1080`；也可确认同一受支持比例且最短边 ≥1000px 的其他具体尺寸 |
| 方向 / 格式 | 与比例一致的竖版或横版 / PNG（RGB） |
| 平台额外限制 | 逐项记录，发现冲突在 H1 报告并等待确认，不承诺全部平台可直接上架 |
| 规格来源 / 用户确认 | 来源、提交版本及批准消息证据、范围、结果版本；未经真实消息批准一律 `Pending` |

H1 获批的 Canvas Specification 是 H2 提案/预览、双版 spec、QA 与 H3 交付的统一基线。`verify_kv.py --expected-width ... --expected-height ...` 仅对照人工从批准记录填写的数值；spec 本身和命令行参数不能证明用户曾批准。修改画布比例或平台限制须重开 H1；原有项目的已提交提案与批准版本不因 Skill 更新而自动变动。

## 8. Project Style Constraint Record

每条记录标注来源、类别、状态和版本；不能把候选字体或模板写成品牌规范。

| 类别 | 记录内容 | 来源/权威 | 状态 | 版本 |
| --- | --- | --- | --- | --- |
| Skill 全局硬约束 | 默认 4:5、H1 可选经验证的 16:9、双版、事实不编造、文字由 spec 渲染、H3 前不进 outputs 等 | 本 Skill | 固定 | `skill-v1` |
| 已确认品牌硬约束 | 官方字体、品牌色、Logo 用法、禁用元素、平台限制；未提供项明确记录“未提供” | H1 人工确认的品牌资料/用户要求 | H1 后冻结 | `brand-v...` |
| AI 风格建议 | 各方案的视觉关键词、字体策略候选、配色候选、版式与骨架建议 | AI 提案 | H2 前各版本均为候选；仅用户批准的方案/版本在 H2 后冻结 | `direction-[ID]-v...` |

H1 必须确认官方字体、品牌色和禁用元素；H2 必须记录获批方案 ID/版本、用户消息证据、批准范围，并冻结该方案的视觉关键词、字体策略、配色和版式。未获选方案与概念预览不进入冻结范围；现有字体和视觉模板仅是候选，除非 H1/H2 明确批准，否则不强制套用。

## 缺口处理规则

| 缺口 | 处理 |
| --- | --- |
| 任务涉及促销但没有价格/活动时间 | 阻塞项，必须问；不允许猜，也不能用“待确认”支持正式交付 |
| 任务不涉及促销 | 不要求价格/活动时间；不要为了模板填入促销字段 |
| 没有卖点证据 | 只写商品客观属性（材质、尺寸、结构），不写效果承诺 |
| 没有官方 Logo | 记录“未提供”；可用明确标注的字标占位，并在交付说明标注其不是官方 Logo |
| 没有可靠商品参考图 | 只能规划或输出明确标注的非保真布局概念；无商品、无文字的场景底图仍可用于规划 |
| 受众不明确 | 按平台 + 类目 + 价格带推断，写进 brief 并标注"推断" |
| 中英双版但英文信息缺失 | 以中文事实为准做本地化重写，不新增事实 |
| 甲方给了中英内容母本表 | 把母本落成 `work/brief/content-master.json`，渲染后用 `scripts/check_copy.py` 核对 0 漏项 |

## 交付说明模板
